## Local deployment decision

Retain the existing MTP2/BF16 choices while upgrading the engine and blazux patches to 0.33. In this run the matched recipe passed 156/164 HumanEval+ tasks, versus 155/164 for 0.31 and 154/164 for the new default. It also performed better than the fast recipe in several repeated-prefix cells, and its measured runtime window had no NVIDIA memory-warning messages. The fast recipe offers the larger reported KV pool, but did not justify promotion on this host. These observations are not proof of a general quality difference or of the cause of the driver warning.

To recreate the selected recipe from this checkout:

```bash
PYTORCH_ALLOC_CONF=expandable_segments:True ./flash serve mtp-standard \
  CPUSET= MTP=2 DRAFT_VOCAB=1 KV_DTYPE=auto SEQS=8 \
  BATCH_TOKENS=8192 GPU_MEM=0.80
./flash wait
```

## Interpretation limits

- Sequential order on one shared host; background services, page cache and swap were not reset. The production baseline had been running for weeks, while 0.33 was newly started. Each matrix begins with the same short warmup, not a full table/page-cache prewarm.
- Image download and build occurred after the complete baseline suite, including HumanEval+, and before 0.33 measurement. They did not overlap the paired suites.
- The fast-profile logs reported inference-time Triton compilation for `_qsa_prepare_kernel` and `store_cache_checkpoints_kernel` during the early matrix. The two-wave samples include that cold-shape behavior; they are not a fully warmed steady-state kernel benchmark.
- Even the matched recipe changes engine and patch versions, and automatic KV allocation rose from the reported baseline pool to the 0.33 pool above. That also changes memory available to the mmap page cache. The fast recipe additionally changes KV precision, MTP depth/head, recurrent state, batching, admission and CPU pinning.
- Two throughput waves per cell and one coding answer per task are descriptive samples, not proof of a universal speedup, a causal engine effect or statistical quality equivalence. A ten-minute soak proves only that measured interval. Deliberate client disconnects are recorded separately from completed generation requests.
- Primary retrieval coverage ends at 256k even though serving is configured for 500k. Any additional longer-context validation must be labelled separately.
- Model weights stay the same hybrid checkpoint throughout. This is not a comparison of full-FP8 model weights against NVFP4 weights.

## Verified final serving

The final API reports `0.33.0` with recipe `v033-matched`. Image, command, environment and CPU pinning match the measured recipe: `True`. The KV pool on this boot is 625,748 tokens. Automatic pool sizing may change on restart; the earlier table describes the measured boot.

Both the patched streaming client and the existing application-network generation probe passed (`True` / `True`). Driver messages since this boot: `{'nv_err_no_memory_messages': 0, 'xid_messages': 0, 'other_nvrm_messages': 0}`.

Supplemental final-serving retrieval at approximately 450k input tokens: **3/3 passed**, covering the 10%/50%/90% positions. This is separate from the paired 32k/128k/256k suite, validates beyond the native 262k boundary, and is not a paired throughput comparison.

## Benchmark client follow-up

Auditing the existing `tools/bench_serving.py` found that HTTP-200 SSE error/partial streams could be returned as successful samples. The companion fix validates terminal finish reason, usage and `[DONE]`, surfaces in-stream errors, retains finish reasons and refuses to overwrite earlier result files. Seven loopback HTTP/SSE regression tests cover successful and failed protocol cases. The measurements above use the separately frozen matrix/quality suite linked at the top.
